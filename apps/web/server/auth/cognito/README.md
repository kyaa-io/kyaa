# Cognito opt-in and Privy wallet identity

`AUTH_PROVIDER=privy` is the unchanged default. Cognito is not ready for live activation until the external settings, inventory, migrations and real browser/device checks below are complete.

## Runtime configuration

Cognito requires `AUTH_PROVIDER=cognito`, `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID` (public PKCE app client), `COGNITO_DOMAIN` (HTTPS origin), `COGNITO_REDIRECT_URI` (APP_URL origin + `/api/auth/cognito/callback`), `COGNITO_LOGOUT_URI` (APP_URL origin + `/login`), and `AUTH_COOKIE_SECRET` (32 random bytes encoded as standard base64). `COGNITO_ENROLLMENT_ENABLED` defaults to false. Do not expose the cookie key or refresh tokens through public runtime config.

Configure Google and SignInWithApple in the pool. ID tokens must identify an unambiguous primary `identities` provider entry with the original verified social-provider subject. Configure Privy custom JWT authentication for this pool issuer, client audience and Cognito `sub`. Keep the existing Privy Google/Apple methods enabled throughout dormant-account recovery. Apple must use the same team/group subject namespace as the legacy inventory; verify this with actual accounts before activation.

The code uses Cognito's OAuth authorization-code + S256 PKCE flow, encrypted state/nonce cookie, RS256 JWKS verification and exact issuer/client/token_use checks. It does not send an AWS SDK administrative password call or claim that legacy passwords migrated. The existing Supabase email/password routes and explicit mobile email binding remain active, with their original Supabase Auth client. A migration Lambda or separate legacy-email-to-Cognito enrollment still requires provider configuration and real credentials testing.

## Existing owners and new enrollment

API ownership remains `app_users.id`; the original `privy_user_id`, wallet chain and address never change. `(issuer, subject)` maps uniquely to that UUID. Email is only a conflict guard, never an automatic merge key. A separate Cognito account and existing fan with the same email are blocked pending recovery/review.

Before enabling new enrollment, export all Privy users through authenticated server tooling and join them to the current `app_users` inventory. Prepare a local private input `{users:[{id,linked_accounts:[...]}],owners:[{id,privy_user_id,status}]}`. Run `node apps/web/server/auth/cognito/backfill.mjs INPUT.json OUTPUT.json`. It performs no network calls or database writes and creates the output with mode 0600, refusing overwrite. Keep these files outside Git; they contain personal identifiers.

The output has `artifactSha256`, `expectedOwnerCount`, `expectedPrivyUserCount`, `unownedUsers` and `owners:[{appUserId,privyUserId,accounts:[{issuer,subject}]}]`. Import <=1000 records per call using service-only `import_cognito_legacy_inventory(p_run_id,p_artifact_sha256,p_expected_owner_count,p_owners)`. Use one random run UUID and unchanged hash/count for all batches. Next call `import_cognito_unowned_inventory(p_run_id,p_expected_privy_user_count,p_users)` with <=1000 unowned Privy records per batch, or `[]` once when there are none. This includes verified social subjects and emails for Privy users without an app_users row, which must also block accidental replacement wallets. Then call `complete_cognito_legacy_inventory(p_run_id)`. Completion fails unless every current active owner is covered and the imported owner count and total Privy user count both match. Do not mark an incomplete export complete. Verified Google/Apple subjects, including email-only owners with an empty social-account list, must be represented accurately. Duplicate subjects across different owners fail import. Known local review, retired and Supabase email owners remain in owner coverage with no social subjects; only actual `did:privy:` identities count toward the Privy export total. Unknown local namespaces or active deleted owners fail preparation.

Set `COGNITO_ENROLLMENT_ENABLED=true` only after this completes. New enrollment still fails closed when coverage is incomplete; existing owners can start login and recover through an exact verified provider subject. Shared Privy session synchronization atomically records verified live owner/provider bindings with the existing UUID and wallet, including native signups and previously unowned exported DIDs. This extends coverage without modifying historical snapshots or merging by email. With the flag false, only existing-provider cohorts can recover; this is not a complete public signup rollout.

Apply `20261130000600_cognito_live_inventory.sql` as the existing schema owner before deploying callers of `sync_privy_identity_with_provider_accounts`, then reload the PostgREST schema cache and verify the service-only RPC is exposed. An existing uncovered Privy owner can be repaired through the same verified session path; do not fabricate provider claims or edit completed exports. Regression checks: `supabase/tests/cognito_live_inventory.sql` and the disposable-database-only `cognito_live_inventory_concurrency.sh` run in the backend security suite.

A verified Cognito provider subject matching an imported owner goes to `/auth/cognito/link`, where Privy OAuth uses `disableSignup:true`. Both live Cognito and Privy proofs, the original DID and actual wallet address must match before `useLinkJwtAccount().linkWithCustomJwt(idToken)` and final server verification. A successful link is persisted only after the server reads the matching `custom_auth` account from Privy. The SDK's JWT sync remains disabled until that mapping exists.

A subject and email both absent from the complete inventory receive a server-side 10-minute, single-use enrollment permit. The same provider's Privy first OAuth runs automatically with signup enabled; the server verifies its provider subject, DID and wallet before linking. Pending proof reservations support retry/dormant recovery without issuing another wallet. Existing email-only users are explicitly directed to their original email flow; the app never creates a replacement wallet for them.

## Cookies, API and logout

Browser cookies contain opaque random lookup keys, with `__Host-`, HttpOnly, Secure, SameSite=Lax and Path=/. Access/ID/refresh tokens are AES-256-GCM encrypted in private DB session rows. Sessions last at most 24 hours, and refresh happens server-side. `/api/auth/cognito/session` returns access and linked wallet tokens only through a no-store same-origin response; the client keeps them in memory. Existing UI call sites use the common `useByUsAuth` adapter and retain Bearer request contracts. Cognito Bearer values have the `kyaa-cognito:` prefix. Invalid Cognito tokens never fall back to Privy verification. Privy tokens remain accepted for legacy clients and explicit wallet linking.

Browser logout revokes the Cognito refresh token and deletes the local session before clearing client state. Cognito's offline JWT checks do not independently query token revocation; already-issued access tokens remain bounded by their configured expiry. Configure a short access-token lifetime and verify the intended logout policy before activation. Browser Hosted UI session logout URL is returned by the endpoint; callers should use it when full upstream sign-out is desired.

## Flutter system-browser contract

Flutter 0.11 supports JWT wallet login but cannot do the first Privy account link. It must open the system browser for the first connection/recovery. Configure exactly one registered native callback in `COGNITO_NATIVE_REDIRECT_URI`; the server never accepts a caller-supplied redirect URI.

1. Flutter generates an S256 verifier (43–128 unreserved characters), its base64url SHA-256 challenge and a random state (16–128 base64url characters). Store verifier/state in OS secure memory/storage.
2. Open the canonical application `/api/auth/cognito/start?provider=google|apple&returnTo=` with the URL-encoded relative return path `/auth/cognito/native/finish?challenge=...&state=...`.
3. The browser completes Cognito and, if needed, the existing Privy linking flow. Native finish POSTs `/api/auth/cognito/native/issue` with `{challenge,state}` using the authenticated HttpOnly cookie. The server returns the configured native callback with only a random one-time `code` and state. It contains no token.
4. Flutter compares state exactly, then HTTPS POSTs `{code,verifier}` to `/api/auth/cognito/native/exchange`. The DB atomically consumes the 60-second handoff only with the matching challenge; replay and wrong verifier fail. The response body contains `accessToken`, `walletToken`, `expiresAt` and opaque `sessionToken`. Keep sessionToken in Keychain/Keystore and walletToken only as required by the Privy SDK.
5. Exchange and refresh also return the verified `appUserId`, `privyUserId`, `walletAddress`, and `chainId`. After Privy JWT login, compare its DID and wallet to these values before confirming the app session. Use the prefixed accessToken for existing API Bearer calls. POST `{sessionToken}` to `/api/auth/cognito/native/refresh` for renewed tokens within the 24-hour server-session limit. POST the same body to `/api/auth/cognito/native/logout` to revoke the refresh token and expire the server handle; only clear local credentials after success. Already issued access tokens retain their short validity. Do not send tokens in URLs or logs.

The companion Flutter checkout implements this contract. Its simulator build and launch passed, but the user deferred native OAuth and device validation on 2026-10-24. Native end-to-end refresh/logout and Apple reauthentication/deletion remain activation checks.

## Hosting and data dependencies

CloudFront must overwrite `X-Forwarded-Host` with the viewer Host and preserve the HTTPS forwarded protocol; only trusted CloudFront origins may reach the ALB. The OAuth callback validates the canonical origin or this trusted forwarding pair. Stateful auth and private routes must never be CDN cached.

`POSTGREST_URL` and `POSTGREST_SERVICE_TOKEN` are optional together; HTTPS or loopback HTTP sidecars only, token >=40 chars. Legacy Supabase settings remain required while email auth is active. `AWS_STORAGE_ENABLED=true` requires AWS_REGION, distinct S3_PUBLIC_BUCKET/S3_PRIVATE_BUCKET and an HTTPS ASSET_PUBLIC_BASE_URL. Storage does not change the authentication issuer.

## Final Cognito email phase

`EMAIL_AUTH_PROVIDER=legacy` preserves Supabase password verification by default. Set `EMAIL_AUTH_PROVIDER=cognito` only after the migration trigger, credential inventory and email pool client are ready. `COGNITO_EMAIL_USER_POOL_ID` and `COGNITO_EMAIL_CLIENT_ID` select a separate password/refresh pool and client; using the social pool for email is rejected. This prevents social email aliases from capturing a legacy email account before password migration. Browser/native OAuth and Privy custom-JWT wallet auth remain on the social pool. The client must allow USER_PASSWORD_AUTH and REFRESH_TOKEN_AUTH. This uses the migration trigger rather than SRP, which cannot send the old password to the verifier. Existing login/refresh/logout request and response fields remain unchanged: `accessToken` stays `kyaa-email:<three-segment JWT>`, `userId` stays `supabase:<original UUID>`, and `appUserId`, `expiresAt` in seconds and profile retain their existing meanings. The wrapper has a strict distinct issuer and `auth_source=cognito-email`, carries only the legacy UUID and session handle, and is signed with HS256. The refresh response contains an opaque random refresh handle; Cognito refresh credentials remain encrypted server-side. Rotation is atomic, and revoked/replayed sessions fail the live gate.

The operator imports `auth.users` id, normalized email, encrypted_password, email_confirmed_at, banned_until, deleted_at and the explicit existing `mobile_email_login_bindings` app_user_id/enabled state into `public.legacy_email_credentials`. Import only existing explicit email bindings; do not infer ownership from email. The table contains sensitive bcrypt hashes and has no app-role SELECT privilege. Use a restricted operator connection or private encrypted import artifact; never place hashes/passwords in logs, Terraform state or source control.

Package `migration-lambda.mjs`, production `pg` and the official AWS RDS `global-bundle.pem` in a Lambda ZIP. The handler uses verify-full TLS semantics (`rejectUnauthorized:true` and the official CA). Connect as a dedicated LOGIN role that inherits only `legacy_auth_migrator`, never service_role or a table-owner role. Configure PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD through the approved secret mechanism and set COGNITO_EMAIL_USER_POOL_ID/COGNITO_EMAIL_CLIENT_ID. The handler checks the incoming pool, client and UserMigration_Authentication event, verifies the password with the restricted `verify_legacy_email_password` function and returns CONFIRMED without a password-reset step. It has no event/password logging. Set PostgreSQL parameter/error audit logging to omit bind values for this role.

Add immutable Cognito string attributes `legacy_user_id` and `app_user_id`; the migration trigger alone writes these. Exclude both from every app client's WriteAttributes and include them in the email client's ReadAttributes. Existing owner lookup uses the signed legacy UUID plus the imported explicit binding, never email alone. Disabled, unconfirmed, banned, deleted, admin and revoked Apple identities remain blocked.

Deploy migration 20261129041000 with the original identity migration. Its SQL test covers UUID/DID preservation, bcrypt failure, live owner state, role grants, refresh rotation and revocation. Pending accepted email deletion continues to verify the signed wrapper and approved deletion snapshot even after the provider is removed. Cognito provider deletion is idempotent and runs before the existing provider-cleanup completion marker.

The complete removal of Supabase still depends on the main database import dropping/replacing legacy auth.users/auth.sessions foreign keys and the legacy RPC branch, plus removing legacy Auth secrets only after old Supabase tokens have expired. This code does not claim those operator steps ran. Existing email-only Privy wallets without a reauthenticatable Privy provider remain on their existing wallet; the code never creates a replacement to bypass that limitation.

Official references: [Privy external JWT setup](https://docs.privy.io/authentication/user-authentication/jwt-based-auth/overview), [Privy JWT usage](https://docs.privy.io/authentication/user-authentication/jwt-based-auth/usage), [Privy account linking](https://docs.privy.io/user-management/users/linking-accounts), [Cognito ID token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-id-token.html), [Cognito migration flow](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html).

`LEGACY_EMAIL_AUTH_ENABLED=true` preserves live Supabase-token verification and deletes both old Supabase and new Cognito email providers when appropriate. Set it false only for the final Cognito-email cutover after existing Supabase access tokens have expired and pending deletions have been checked; old Supabase tokens then fail locally before any Supabase Auth network call. New Cognito JWT wrappers and accepted Cognito-email deletion retries remain valid. Final Supabase configuration removal is guarded by the main data adapter rollout, not by invented URL/key placeholders.
