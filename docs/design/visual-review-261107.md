# 시각 검수 체크리스트와 평가 루브릭 (261107-2)

기계 검사(`node scripts/design-lint.mjs`, `docs/design/review-rules-261107.md`)가 못 보는 것을 사람이 390·1440 실제 화면에서 본다. 토큰·공통 컴포넌트 기준은 `DESIGN.md`의 "디자인 시스템 기준" 절이다. 다음 피드백 묶음도 이 목록과 루브릭을 같은 방식으로 쓴다.

## 1. 쓰는 방법

1. 변경한 화면을 **390과 1440** 폭의 실제 앱에서 원본 크기로 연다. 한 화면 캡처 모음(contact sheet)만 본 것은 통과가 아니다.
2. 비로그인·로그인·운영자 상태(해당될 때), ko·en·ja(긴 문구는 de), 값이 0인 상태와 가득 찬 상태, 로딩 전후, `prefers-reduced-motion`을 확인한다.
3. 기준 화면이 있으면 나란히 놓고 본다. 측정값이 맞아도 구성·밀도·끝선·위계가 어긋나면 "아니오"다.
4. 아래 질문 중 하나라도 "아니오"면 완료로 보고하지 않는다. 보고에는 **본 상태**와 **못 본 상태**를 나눠 적는다. 못 본 것은 못 봄으로 적고 통과로 쓰지 않는다.
5. 합성 데이터·로컬 화면은 그렇다고 밝힌다. 운영 화면처럼 쓰지 않는다.
6. 기계 규칙 통과는 필요조건일 뿐이다. 어떤 항목도 린트 통과만으로 통과시키지 않는다.

## 4. 평가 루브릭

3인 평가 루프용 고정 루브릭이다. 저장소 안이 아니라 보드에 있다.

- 위치: `~/.local/share/kyaa-t3/board/tasks/doc-261107-2/rubric/`
  - `rubric.json` — UI/UX(U1~U12, 304 coverage), 기능/QA(Q1~Q10, 304), 성능(P1~P9, 48). 목표는 평균 95·개별 90·차단 0. 점수 앵커 0~5.
  - `rubric.sha256` — 최초 해시(`9a1bd074…b611395`). **`rubric.json`을 고치면 해시가 달라져 검증이 실패한다.** 기준을 바꿔야 하면 이 폴더를 고치지 말고 새 버전을 새 폴더에 만든다.
  - `evaluator-brief.md` — 평가자 지침(받는 것, 하는 것, 안 하는 것, 출력 형식, 재채점, 서버·로그인 방법).
  - `verify.mjs` — 구조와 회차 검증. `gen-rubric.mjs` — 생성기(해시 기록 뒤에는 돌리지 않는다).
  - `round-NN-<영역>.json`, `round-NN-<영역>-defects.md`, `round-NN-<영역>/` — 지난 회차 결과와 증거.
- 규칙 원문: `~/.local/share/kyaa-t3/board/reports/doc-261107-2-review-rules.md`(K1~K12 → N·V·F 매핑, 위 V 목록의 출처). N·F 실행법은 `docs/design/review-rules-261107.md`.

### 실행

```
cd ~/.local/share/kyaa-t3/board/tasks/doc-261107-2/rubric
node verify.mjs                          # 루브릭 구조·합계·앵커·해시 검사
node verify.mjs round-02-uiux.json ...   # 회차 파일 검사(영역별 100점, 평균 95, 개별 90, 차단 0, coverage, 증거 해시)
```

종료 코드: 0 통과, 1 미달·차단·미검증(사실이면 그대로 둔다), 2 입력 오류(기준 변경·coverage 누락·추가).

회차 순서
1. 평가 대상 커밋과 주소·포트, 시험 계정 이름(이메일 제외)을 평가자에게 `evaluator-brief.md`와 함께 준다. 평가자는 서로의 점수·보고서를 열지 않고 산출물을 고치지 않는다.
2. 평가자별로 `round-NN.<영역>.json`을 만들고 coverage ID를 `rubric.json`과 정확히 같은 집합으로 채운다. 못 본 것은 `unverified`, `score: 0`이다. 5점은 앵커 조건을 모두 충족하고 결함·증거 공백이 없을 때만 준다.
3. 시각 증거는 원본 크기 캡처와 `sha256`. 성능은 실측만 쓴다(390 모바일 에뮬·4G 스로틀·3회 중앙값, 1440 데스크톱).
4. 증거 파일마다 `shasum -a 256`을 적고, 제출 전에 `verify.mjs`로 입력 오류를 없앤다.
5. 이전에 `open`인 finding은 지우지 말고 새 증거로 `resolved`로 닫는다. 사용자가 통과 뒤 결함을 지적하면 같은 원인을 공유하는 모든 화면의 통과를 무효로 하고 변형까지 다시 본다.

평가 서버(2회차 이후, 평가자 지침 기준): `~/.local/share/kyaa-t3/kyaa-t3 localdev-prod <worktree> 3000`으로 production 빌드를 띄운다(준비는 `/api/health/live`). 개발 서버의 컴파일 지연이 만든 스켈레톤은 평가하지 않는다. 로그인은 `kyaa-t3 local-login <계정>`의 storageState를 쓰고 30분마다 갱신한다. 끝나면 오케스트레이터가 `kyaa-t3 localdev <worktree>`로 되돌린다.

차단 결함(모든 영역 공통): 저장·지급·업로드 실패, 콘솔 런타임 오류, 비로그인에서 UI 소실, 언어 선택 소실, 모의 데이터로 통과, 기준선 대비 design-lint 신규 위반 증가, 측정하지 않은 항목을 통과로 기록.
