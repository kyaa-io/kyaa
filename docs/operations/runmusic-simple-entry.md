# RUNMUSIC 간편 응모 운영

2026-10-23 구현 기준. 이 문서는 운영 반영 완료 기록이 아니다. 기존 QR과 `/connect/runmusic`을 유지하며 `/connect/runmusic/results`에서 본인 결과를 확인한다.

## 확정 동작

- 마감·결과 예정: 2026-10-24 23:59 KST (`2026-10-24T14:59:00Z`). 실제 공개는 그 시각 이후 첫 워커 실행 시점이다.
- 기존 등록자는 그대로 포함한다. 신규 등록은 RUNMUSIC 좋아요가 필요하며 계정당 한 번, 모든 참여자의 가중치는 1이다. 이전 미션은 추가 확률을 주지 않는다.
- 무작위 순위 1~15는 안동참마요거트 1L, 16~165는 스타벅스 1만원 상품권이다. 참여자가 적으면 실제 참여자 수까지만 선정한다. 이미 만든 추첨은 재생성하지 않는다.
- 신규 참여자는 카카오톡 ID를 입력한 뒤 응모를 확정한다. 응모·암호화 연락처·운영 알림 대기열이 함께 저장되며, 저장 실패 시 새 응모도 생성되지 않는다. 기존 참여자의 연락처 수정 실패는 기존 응모에 영향을 주지 않는다. ID의 실제 소유 여부는 인증하지 않는다. 연락처는 서버에서 AES-256-GCM으로 암호화하고, 관리자 목록에는 마스킹 값만 보인다. 권한 있는 관리자의 개별 열람은 감사 기록에 남는다.
- 미당첨 연락처는 발표 시 삭제한다. 당첨 연락처는 수령 처리일, 미수령은 추첨일 기준 30일 뒤 삭제한다. 탈퇴·비활성화 시에도 삭제한다.
- 결과 알림은 기존 알림 목록과 이메일 경로를 사용한다. 카카오·푸시는 보내지 않는다. 이메일 수신 동의, 검증된 주소, 활성 계정, Apple 계정 및 발송 정책을 그대로 적용하므로 응모자 전원에게 이메일이 전달된다는 뜻은 아니다.

## 반영 순서

1. 새 마이그레이션 `20261129040000_runmusic_simple_entry.sql`, `20261129041000_runmusic_result_notifications.sql`, `20261129042000_runmusic_explicit_campaign_updates.sql`을 순서대로 적용한다. 기존 이벤트·등록·추첨 데이터는 지우지 않는다. 새 코드가 v2 RPC를 사용하므로 DB를 먼저 반영한다.
2. 웹 서버에 `RUNMUSIC_CONTACT_ENCRYPTION_KEY`를 설정한다. 암호학적으로 안전하게 생성한 32바이트 키의 64자리 hex 값이며 `NEXT_PUBLIC_`에 넣지 않는다. 키 자체를 로그·명령행·저장소에 남기지 않는다. 연락처가 남아 있는 동안 같은 키를 유지한다. 키가 없으면 신규 응모 확정과 연락처 저장·열람이 실패하며 기존 응모 기록은 유지된다.
3. 웹과 notification worker를 같은 변경으로 배포한다. 워커가 `process_due_runmusic()`과 `purge_due_runmusic_contacts()`를 호출하는지 확인한다. 이메일 발송을 꺼도 추첨 시각 확인과 연락처 삭제는 계속 실행한다.
4. 아래 발송 설정을 확인한 후 관리자 RUNMUSIC 화면에서 자동 발표를 켠다. 기본값은 꺼짐이다. 마감 후 켜면 다음 워커 실행에서 바로 추첨·공개할 수 있다. 수동 추첨도 마감 이전에는 거부된다.
5. 준비한 홈 배너를 기존 관리자 API로 등록한다. `node scripts/prepare-runmusic-home-banner.mjs`는 네트워크 없이 미리보기만 출력한다. 실제 반영은 `RUNMUSIC_APP_URL`, `RUNMUSIC_ADMIN_TOKEN`을 비공개 환경으로 전달하고 `--apply`를 지정한다. 스크립트는 이미지 업로드→배너 등록·공개→첫 순위 이동을 수행하며 다른 배너의 상대 순서는 보존한다. 기존 문구·이미지가 수동 편집됐으면 덮어쓰지 않고 중단한다. 중간 실패 시 업로드나 초안은 남을 수 있으며 확인 후 일치하는 상태에서 재개한다.

## ID 입력 후 응모와 운영 Telegram 알림

추가 마이그레이션 `20261129044000_runmusic_contact_entry_telegram.sql`을 웹보다 먼저 적용한다. 신규 웹은 `enter`에 ID를 필수로 받아 v3를 호출하며, 기존 조회·연락처 수정과 이전 웹의 v2는 보존한다. 이번 추가 변경은 웹 배포만 필요하고 결과 추첨 워커 설정은 바꾸지 않는다.

웹 서버 전용 설정은 `RUNMUSIC_TELEGRAM_MODE=enabled`, `RUNMUSIC_TELEGRAM_BOT_TOKEN`, `RUNMUSIC_TELEGRAM_CHAT_ID`다. 운영 대상은 확인된 `KYAA-ALERT` 그룹이며 배포 안내용 Bug Report 방과 다르다. 기본 모드는 비활성이다. 기존 연락처 암호화 키를 재사용하고 브라우저·워크 큐·로그에는 이메일이나 ID 원문을 남기지 않는다.

응모 트랜잭션이 끝나면 Next `after`에서 즉시 전송을 시도한다. 실행되지 못한 작업은 `CRON_SECRET`으로 보호된 `/api/internal/runmusic/telegram/process`가 매분 최대 3건씩 처리한다. 대기열에는 회원 참조만 저장한다. 전송 시작 시점의 검증된 이메일과 최신 ID를 사용하며, 시작 후 변경된 ID는 이미 시작한 알림에 반영하지 않는다. 기존 참여자·ID 수정·동일 요청 재실행에는 새 알림을 만들지 않는다.

활성 계정·이메일·보존 가능한 연락처가 없으면 `skipped`로 기록한다. 명확한 Telegram 429 응답만 최대 5회 시도하고, 거절·잘못된 연락처는 `failed`, 시간 초과·5xx·비정상 응답은 `unknown`으로 끝낸다. 전송 성공 뒤 DB 기록이 실패해도 만료된 `sending`은 `unknown`이 되어 자동 재전송하지 않는다. 알림 실패는 이미 확정된 응모를 취소하지 않는다.

운영 점검은 원문을 열람하지 않는 집계로 시작한다.

```sql
select state, reason, count(*)
from public.runmusic_telegram_deliveries
 group by state, reason;
```

`unknown`은 대상 방의 실제 수신 기록과 대조하기 전까지 재전송하거나 receipt를 지우지 않는다. 이번 검증의 연결 테스트는 합성 이메일·ID를 명시한 별도 메시지로 수행하며 실제 회원 응모나 조기 추첨을 만들지 않는다.

## 자동 발표 전 확인

DB 운영 연결에서 다음 읽기 전용 조회로 확인한다. 키와 연락처 원문을 출력할 필요는 없다.

```sql
select slug, published, entry_closes_at, results_at, auto_publish_enabled,
       draw_id, results_published
from public.runmusic_campaign;

select channel, mode, activated_at, allowed_kinds
from public.fan_notification_delivery_control where channel = 'email';
```

이메일은 워커의 `NOTIFICATION_EXTERNAL_MODE=ses_email` 및 기존 SES 설정이 정상이어야 한다. DB email mode는 `enabled`여야 하며, `allowed_kinds`가 제한 배열이면 기존 항목을 보존하면서 `runmusic_result`를 포함해야 한다. `null`은 종류 제한이 없다는 뜻이다. 이번 마이그레이션은 현재 발송 설정을 변경하지 않는다.

`activated_at`보다 **나중에 생성된 알림만** 발송 대상이다. 따라서 이메일 발송 설정을 먼저 확인하고 자동 발표를 켠다. 기존 enabled 설정을 불필요하게 다시 활성화하면 cutoff가 바뀐다. mode 변경이 필요하면 기존 provider 중지·진행 중 실행 종료 절차와 `configure_fan_notification_delivery`를 사용하며, 발송을 위해 cutoff를 과거로 돌리지 않는다. 발표 뒤 게이트를 바꿔 놓고 기존 알림이 자동 복구된다고 가정하지 않는다.

운영에서는 승인된 테스트 계정으로 응모·연락처 저장과 개별 관리자 열람, 로그인 복귀, 개인 결과 경로를 확인한다. 로컬 검증은 실제 SES 수신이나 운영 비밀값 설정을 검증하지 않는다.

## 결과 확인과 복구

관리자 화면은 실제 pending/sent/failed/skipped 건수를 표시한다. sent는 전송 처리 완료이며 수신함 도착을 보증하지 않는다. 동시 워커·수동 실행은 같은 캠페인 잠금을 사용하고 이미 공개한 결과를 재생성하지 않는다. 실패 시 원인과 현재 draw ID·알림 상태를 먼저 확인한다. 결과를 초기화하거나 알림 receipt를 지워 재발송하지 않는다.

문제가 있으면 관리자에서 자동 발표를 끄고 기존 발송 게이트로 이메일을 중지한다. 이미 생성된 결과·참여 기록·암호화 연락처는 보존한다. 키 변경만으로 기존 암호문을 복구할 수 없으므로 연락처 보존 중 키를 임의로 교체하지 않는다.

## 검증

DB 새 설치·기존 데이터 업그레이드·동시 처리 검증은 backend-security workflow의 RUNMUSIC 단계에 연결했다. 웹 행동·연락처 암호화·알림 투영 테스트, 전체 워커 테스트, 11개 언어 390/1440px 브라우저 검증과 768px 배너 검증을 수행했다. 브라우저 실행법과 예시 데이터 범위는 `apps/web/e2e/runmusic-local/README.md`에 있다. 운영 배포·발송·추첨·CMS 배너 등록은 별도 실행 단계다.

2026-10-23 운영 확인에서 PostgREST의 `safeupdate`가 대상 조건 없는 캠페인 갱신을 거부했다. 캠페인이 한 행이어도 갱신에 `where slug=c.slug`를 유지한다. 관리자 설정 저장은 실제 관리자 API로 확인하며, 예약 추첨은 운영 시각을 당기지 않고 격리 DB의 추첨·동시성 검사로 확인한다. `runmusic_participation.sql`은 설정 활성화·비활성화·revision 충돌과 두 함수의 갱신 대상 조건을 검사한다.

같은 날 운영의 기존 로그인으로 결과 링크를 직접 열었을 때 로그인 전환 owner가 비어 있어 로딩이 끝나지 않는 문제를 확인했다. 준비된 기존 세션은 Privy 사용자 ID를 기준으로 복원하고, 로그인 전환 중이거나 owner가 다른 세션은 계속 차단한다. 로컬 브라우저 fixture도 직접 진입과 같은 owner-null 상태를 사용한다. 운영 확인 시 기존 로그인으로 응모·결과 URL을 직접 열어 상태가 표시되는지 확인한다.

2026-10-23 비로그인 진입 오류 제보 시각에 개인 조회의 403 응답을 확인했다. SDK에 복원된 사용자 ID가 있어도 앱 회원 세션이 유효하다는 뜻은 아니다. 개인 조회가 401·403이거나 토큰이 없으면 공개 행사 정보와 로그인 버튼으로 복구하며, 5xx는 재시도 가능한 오류로 유지한다. 이 경로 변경 시 완전한 비로그인과 SDK 사용자만 복원된 401·403 상태를 각각 확인하고, 로그인 이동의 원래 경로·언어 보존과 개인 응모 권한 차단을 검증한다. 실제 회원의 임의 응모는 만들지 않는다.

2026-10-24 복구 검토에 따라 인증 준비 중에는 공개 행사 정보를 먼저 표시하고, 토큰 발급 예외·20초 제한 시간 초과도 공개 조회로 복구한다. 개인 정보 조회와 응모는 준비된 동일 계정에서만 실행한다. 제출 중 401·403이나 토큰 오류는 현재 입력을 유지한 채 로그인 링크를 표시하고 재제출을 막는다. 입력은 현재 화면에서만 보존하며 로그인 이동이나 계정 전환을 넘어 연락처 초안을 저장하지 않는다. 회귀 검증에는 준비 지연·토큰 예외·늦은 응답·제출 인증 실패와 로그인 경로·언어 복귀를 포함한다.
