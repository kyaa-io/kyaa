# Existing kyaa credential replacements

This is separate from the [binding-2 Hub upgrade](KYAA_MIGRATION.md). Each verified old asset receives one same-wallet, same-issuance-key representative on the new Passport/Stamp contract. Old tokens, Hub actions, EAS attestations, dates, points and rewards remain unchanged. Old tokens remain visible in external wallets.

The immutable `KyaaCredentialMigrator` accepts only an operator-submitted Merkle proof against a Timelock-registered batch. Each leaf binds the chain, migrator, environment, old/new contract, old token/key/owner/URI, new URI and original Hub action. It verifies original ownership and current source validity, forbids duplicate source/target mappings, and enforces batch count, mint count, expiry and pause controls. Pure legacy mints have no invented Hub action. Invalid, revoked, ambiguous and unresolved assets are held.

## Execution and recovery

1. Deploy the compatible web reader before applying `20261014020000_kyaa_existing_credential_replacements.sql`. The old web schemas reject the added mint fields; the new reader accepts the old DB response. Applying the migration creates no replacement mapping and changes no issuance route.
2. Use the preserved original Migrator artifact (SHA-256 `b7cca80c6383bdc8296366f2ddde3343016e9acec23d54d50a4524bf89f0bf2e`); do not rebuild it. All replacement commands require `--artifact <absolute-original-artifact-path>`. Run `scripts/replace-existing-nfts-giwa.mjs inspect --artifact <absolute-original-artifact-path> --manifest <private-plan> --rpc-file <private-rpc-file>` and verify the exact review hash, deployed runtime/immutables, operation and readiness.
3. At readiness, use `activate` with those arguments and `--approved-hash <review-hash>`. It executes the exact scheduled role grants and root registration, then verifies the roles and batch. Never replace or reschedule an unknown transaction.
4. Start `migrate` with the same arguments, `--database-env <private-env-file>` and `--limit 1`. It rechecks the current original DB reference, wallet, eligibility and aliases, broadcasts once, then persists the mined receipt. It does **not** publish a DB mapping before finality.
5. After the receipt is finalized, run `reconcile` with the same arguments. It verifies the canonical event, forward/reverse mappings, target key/owner/supply/URI and finalized block hash, then atomically appends the mapping and aliases. Check the first representative in its owner's web flow, the public source record and an external wallet before continuing in bounded batches (`--limit 100`). Run `reconcile` after each batch reaches finality.
   For type-specific canaries, use `--leaf <reviewed-manifest-leaf> --limit 1` with `migrate` and `reconcile`. This selects one existing manifest entry without changing its order, hash or proof; unknown leaves and larger limits are rejected. A completed selection never falls back to another entry.
6. Repeat `migrate` and `reconcile` using the same manifest and journal. Mined entries are skipped by `migrate`; reconciled entries are skipped by both. Signed-only entries are recovered through their existing hash; unknown broadcast results stop without re-signing. A DB failure after mint is repaired by `reconcile`, never by issuing a second token.
7. Re-inventory after the old issuance backlog drains. Explain every held asset and create a separately reviewed, Timelock-authorized catch-up batch for newly eligible assets. Do not edit the registered manifest/root or silently omit held assets.

The signer lock is shared across checkouts in Git metadata. Preserve it and the signed journal on uncertain transmission; investigate before resuming. The script caps fees and gas, bounds each run to 100 entries, and requires the exact reconstructed manifest hash. A failure stops the run. Finalized DB rows are append-only, RLS-protected and unavailable to browser/service-role direct writes. Native source validity is rechecked by the trusted public snapshot before owner responses use a replacement; unavailable proof falls back to the original reference.

## Verification

Focused contract tests cover authorization, Merkle/owner/URI boundaries, duplicate/replay behavior, revoked sources and ERC-721 callback reentrancy. A private pinned GIWA fork at block 38593218 exercises legacy Passport, current-Hub Stamp and legacy-Hub Stamp replacements while preserving original ownership, metadata and Hub/EAS records. Run it with `RUN_KYAA_REPLACEMENT_FORK=true`, `KYAA_REPLACEMENT_FORK_RPC` and the private ABI-encoded `KYAA_REPLACEMENT_FORK_SAMPLES`; without those inputs it deliberately skips.

Node tests cover inventory/alias deduplication, held assets, manifest reconstruction, Merkle proofs, runtime eligibility, bounded recovery and finality. SQL checks replay the full migration chain and exercise append-only ownership projections, alias reconciliation, membership withdrawal and duplicate reconciliation. Web tests verify canonical replacement proofs, current source continuity, original-reference fallback and unchanged counts. Actual 390px/1440px local fixture screenshots cover the unified web artwork; real replacement-wallet QA remains required after activation.

Inventory `verify` accepts an optional `--source-receipts <private-hints.json>` file with format `{"format":"kyaa-source-receipt-hints-v1","hints":[{"hub":"<trusted Hub address>","actionId":"<latest action ID>","txHash":"<transaction hash>"}]}`. These locators are used only when the latest ACTIVE action has no DB credential-reference group. The verifier reads the canonical receipt at or before the fixed finalized snapshot and verifies its complete credential references against the existing EAS attestation; it never substitutes for partial DB references or writes receipt hints into the database. The flag is rejected outside `verify`, and the hints file remains private.

## Follow-up batches and direct legacy assets

`prepare-followup --source-kind entity|direct_legacy` creates a separately reviewed `kyaa-existing-nft-followup-plan-v1` for the existing Migrator `0xd72c1ac7f0ec0fcfe596050cff21f6fb477cee0c`. Use the usual private `--verified`, `--metadata`, `--manifest` and `--rpc-file` inputs. Entity batches retain the existing verified-inventory and metadata v1 formats and business eligibility checks. Each follow-up batch has one explicit source kind. It schedules exactly one `registerBatch` call with `schedule-followup`; there is no deployment, role grant or arbitrary target. The existing 48-hour minimum, exact review hash, `activate`, bounded `migrate`/`reconcile`, signer lock and signed journal apply. `schedule-followup`, activation and minting require `--database-env` for fresh source and replacement-uniqueness checks. The original v1 plan reconstruction and calldata remain unchanged.

Direct legacy assets require a separate private `kyaa-direct-legacy-proof-v1`, never an absent business entity or a zero source Hub inferred from an entity inventory. Run `direct-legacy-nfts-giwa.mjs verify --proof <proof> --original-metadata <raw-CID-proof> --rpc-file <rpc> --database-env <env> --output <verified>` to recheck the original canonical mint receipt, exact direct mint calldata, historical minter role, current owner/key/supply/URI, and absence of business, alias, legacy-job, native-outbox and credential associations. The proof binds both trusted Hubs' reviewed full-lifespan absence baseline, exact asset filters, inclusive gap-free ranges and canonical finalized watermark. Its fingerprint records operator-captured evidence; a fingerprint or declared range list alone does not prove that the original RPC query was complete. Before every new signature the verifier checks that baseline's canonical hash and scans every subsequent block through a fresh finalized head. A new Hub reference stops the direct lane.

The read-only `metadata --verified <direct-verified> --output <documents>` mode renders documents without uploading. Only the validated original credential types are supported; unknown types and unproven membership eligibility stop. Original known traits are preserved, while existing kyaa renderers supply the name, description and artwork without inventing a business entity. After separately publishing the exact documents, supply `kyaa-direct-legacy-metadata-v1` with each document's `digest`, `uri`, `document`, actual published UTF-8 `raw` bytes and `sha256`. Original and new raw-codec SHA256 CIDs, document bytes and expected metadata are bound into the reviewed plan and rechecked before signing. An existing target can be reused only if its owner, key, supply and URI match and no source/target mapping already owns it.

Direct reconciliation first uses the common finalized replacement verifier, then atomically appends only the batch and replacement evidence while locking and rechecking association absence. It creates no replacement-entity links and changes no business records, rewards or points. A failed DB write leaves the same mined journal entry pending for `reconcile`; it does not issue another NFT. Run `RUN_DIRECT_LEGACY_DB_TEST=1 node --test scripts/replace-existing-nfts-giwa.test.mjs scripts/direct-legacy-nfts-giwa.test.mjs` for the guarded disposable PostgreSQL replay and focused recovery tests.

A single orphaned, completed Passport job can be reviewed explicitly without changing the `direct_legacy` source kind. Add `orphanCompletedJob` to that source only: `{format:"kyaa-orphan-completed-job-v1",jobId,ownerAppUserId,jobSnapshot,jobFingerprint}`. `jobSnapshot` is the unchanged complete private database row, including any original worker submission; `jobFingerprint` is the lowercase SHA256 hex returned by `orphanCompletedJobFingerprint(jobSnapshot)` over recursively sorted JSON keys. At most one such exception is allowed per batch. The evidence is bound into the manifest, and every new signature and atomic reconciliation requires the exact same database row, completed Passport v1 identity, original mint transaction/key/token/recipient/creator, no lease, and one active owner with the original GIWA wallet. Any additional job, entity, alias, native legacy-job/key/NFT reference or row drift stops the operation. The original signed transaction is checked against its hash, mint envelope and signer; neither the job nor its payload is modified. Sources without this explicit evidence still reject every matching legacy job. Source snapshots check their actual `existingTokenId` field as well as historical `tokenId`; replacement reconciliation appends evidence only, with no replacement-entity link.
